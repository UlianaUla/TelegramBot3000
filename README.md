# Этап 3: последний товар — правила до изменения кода

Репозиторий для сдачи: [UlianaUla/TelegramBot3000](https://github.com/UlianaUla/TelegramBot3000).

1. Менеджер оформляет поступления, видит on_hand/reserved/available, резервы, движения и задания возвратов в том же Mini App. Начальные остатки нулевые; поступление — явная серверная операция с журналом, не скрытое изменение чисел.
2. Резерв создаётся при подтверждении всего заказа, а не в корзине. Срок по умолчанию 120 секунд, параметр RESERVATION_SECONDS. Серверное UTC-время строго меньше expires_at означает действующий резерв; равенство уже означает просрочку. Задержавшееся подтверждение после срока считается поздним, даже если оплату нажали раньше.
3. Если одной позиции не хватает, весь заказ отклоняется: ни состава заказа, ни частичного резерва, ни движений других позиций. Повтор запроса с тем же ключом и отпечатком возвращает сохранённый результат; изменённый состав под тем же ключом отклоняется.
4. Оплата, отмена и истечение используют BEGIN IMMEDIATE и текущее состояние резерва. Выигрывает первый допустимый зафиксированный переход. Потреблённый резерв нельзя отменить; требуется полный возврат. Выдача повторно склад не списывает.
5. Поздняя успешная оплата создаёт payment_conflict, одно поступление с нулевой себестоимостью и постоянное задание возврата. Она не забирает товар у другого покупателя. Возврат такой оплаты не добавляет склад; возврат принятой продажи восстанавливает товар и себестоимость ровно один раз.
6. При запуске и каждые 5 секунд worker находит просроченные active-резервы и незавершённые задания в SQLite. Возврат выполняется вне транзакции, с постоянным ключом; ошибка и следующая попытка сохраняются. После потерянного ответа проверяется известный ID или повторяется тот же ключ, новая операция не создаётся.

Схема дополнения: inventory → reservations/reservation_items → orders/order_items → payments → finance_operations; inventory_movements объясняет каждую дельту, checkout_requests хранит отпечаток и результат, refund_jobs — повторяемые возвраты. Исторические заказы остаются legacy: никаких повторных списаний или резервов задним числом. Для состояния распродажи используется отдельное orders.stock_state, прежний orders.status остаётся статусом выдачи.

План небольших этапов: (А) схема/поступление/остатки; (Б) атомарное оформление и ключи; (В) деньги, сроки и постоянные возвраты; (Г) бот/Mini App и изолированная HTTP-приёмка. Тестовая ЮKassa сохраняется. Имитатор, управляемые часы и аварийные точки доступны только отдельному локальному тестовому серверу, в публичном API они отсутствуют.

Подробный запуск: [STOCK.md](STOCK.md). Фактические результаты: [STOCK_REPORT.md](STOCK_REPORT.md). Первый сбой и исправление: [STOCK_DEBUG_LOG.md](STOCK_DEBUG_LOG.md).

После обновления склад пуст: менеджер должен оформить явное поступление в Mini App, иначе новые заказы будут отклонены по нехватке. Рабочую базу перед обновлением сохраните локально. Нагрузочные и аварийные проверки изолированы в data/stock-tests и не обращаются к рабочей базе или ЮKassa.

Проверки: `python -m bot.stock_acceptance` (все 13 сценариев, минимум пять повторов конкуренции); изменение параметров: `python -m bot.stock_acceptance --ttl 30 --stock 3 --buyers 12`.

# Книжный магазин «Фолиант» и финансовый Telegram Mini App

Учебный проект: один Telegram-бот обслуживает покупателей и менеджера, один Python-сервер работает с одним файлом SQLite. Покупатель выбирает книги, меняет корзину и оформляет самовывоз. Оплата — тестовая ссылка API ЮKassa или расчёт при получении. Менеджер открывает финансовый кабинет внутри Telegram, видит поступления и возвраты, записывает операционные расходы.

## Сценарий и роли

**Кто покупатель и чего хочет?** Человек хочет выбрать книгу, увидеть достоверную цену, забрать её самовывозом и получить сохранённый номер заказа.

**Что выбирает и какие сведения нужны?** Книги и количество; имя или псевдоним; самовывоз. Телефон и адрес доставки не нужны. Учебные контакты: г. Учебный, ул. Книжная, д. 7, ежедневно 10:00–19:00, foliant-study@example.com.

**Что происходит после подтверждения?** Сервер одной транзакцией сохраняет заказ, снимки состава, цены и себестоимости, очищает корзину. При онлайн-оплате создаётся отдельный pending-платёж. Менеджер видит оплаченные заказы и заказы с расчётом при получении, меняет статус выдачи. Покупатель видит только свои заказы.

**Когда заказ оформлен?** После успешного COMMIT записи заказа и состава. Это ещё не означает оплату. «Оплачено» и финансовое поступление появляются только после проверки успешного платежа у ЮKassa. Кнопка «Подтвердить заказ» выбирает расчёт при получении и поступления не создаёт.

Менеджер определяется числовым ID из MANAGER_IDS. Одного бота достаточно: покупатель и менеджер используют те же заказы в общей базе, данные никуда не копируются. Имитатор по просьбе владельца отключён в боте и API; серверные учебные фикстуры остались только для автотестов. Архивные учебные операции не удаляются автоматически.

## Ассортимент

При первом запуске в пустой каталог записываются шесть вымышленных книг:

- «Тихий переулок» — повесть о городском дворе, 640 ₽.
- «Схемы для начинающих» — учебное пособие, 890 ₽.
- «Остров карманных карт» — приключенческая повесть, 720 ₽.
- «Каталог невозможных вещей» — короткие рассказы, 560 ₽.
- «Практикум по вниманию» — учебные упражнения, 480 ₽.
- «Письма с чердака» — переписка вымышленных героев, 610 ₽.

Цены читаются из products, не из текста сообщения или данных браузера. Начальное наполнение — CATALOG в bot/db.py. Повторный запуск не перезаписывает существующий каталог.

## Путь клиента и финансов

```text
/start → Каталог → Карточка → В корзину
                               ↓
                         Корзина → + / − / удалить
                               ↓
                      Имя → Самовывоз → Проверить итог
                               ├─ Подтвердить → расчёт при получении
                               └─ ЮKassa → pending → succeeded / canceled
                                                        ↓
                                                receipt в журнале
Мои заказы ← номер, состав, статус оплаты, ID платежа

Менеджер → Финансы · Mini App → Открыть Mini App (HTTPS)
                              ├─ Период → сводки и журнал
                              ├─ Расход → expense
                              └─ Полный возврат → refund_pending
                                                   ↓ ответ ЮKassa
                                             refund_succeeded → refund
Менеджер → Новые заказы → Готов к выдаче / Выдан / Отменён
```

Обратные кнопки ведут в каталог, корзину и список заказов. Нулевое количество, пустая корзина и устаревшие кнопки обрабатываются отказом с подсказкой.

## Технологии и точные зависимости

Python 3.10+; SQLite стандартной библиотеки; aiogram 3.31.0; aiohttp 3.14.3; python-dotenv 1.2.4; yookassa 3.12.1. Версии закреплены в requirements.txt. Mini App — HTML/CSS/JavaScript без фреймворка. Node.js нужен только для необязательных проверок JavaScript, не для запуска магазина.

## Запуск на чистой Windows

Откройте cmd в папке проекта. В примерах путь соответствует компьютеру автора; на другом компьютере замените его.

```bat
cd /d "C:\Users\User\Desktop\Telegram bot"
py -3 -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
copy .env.example .env
notepad .env
```

Копируйте шаблон только если .env ещё нет. В PowerShell можно выполнить Copy-Item .env.example .env. Настоящий .env не публикуется.

Локально заполните BOT_TOKEN, YOOKASSA_SHOP_ID, YOOKASSA_SECRET_KEY и учебную почту YOOKASSA_RECEIPT_EMAIL. Секреты берутся в BotFather и кабинете тестового магазина ЮKassa, в чат их передавать не нужно. PROVIDER_TOKEN для redirect-ссылки API не требуется.

```bat
.venv\Scripts\python.exe -m bot
```

Команда запускает polling и HTTP на http://127.0.0.1:8080/. В Telegram отправьте /start, затем /id. Число из /id впишите в MANAGER_IDS и перезапустите программу. Для нескольких менеджеров используйте ID через запятую. Остановка — Ctrl+C; одновременно должен работать один экземпляр бота.

## Mini App и HTTPS

Обычный локальный HTTP недоступен Telegram как Mini App. Для демонстрации остановите предыдущий запуск и выполните:

```bat
.venv\Scripts\python.exe -m bot.launch
```

Если зависимости установлены в обычный python, можно дважды открыть start-miniapp.cmd — он вызывает python -m bot.launch. Запускатель скачивает cloudflared из официального репозитория, если его ещё нет, получает временный публичный HTTPS-адрес, записывает MINI_APP_URL в локальный .env и запускает магазин. Нужен интернет. Если менеджер ещё не указан, потребуется числовой ID из /id.

В Telegram: /start → «Финансы · Mini App» → «Открыть Mini App». Можно использовать /finance. Это inline-кнопка web_app, кабинет открывается внутри Telegram. Пользователь без роли менеджера получает отказ; видимость кнопки не даёт доступа.

Окно запуска должно оставаться открытым. После нового запуска временный адрес меняется: запросите новую кнопку через /finance. Для постоянного размещения используйте собственный HTTPS-сервер, MINI_APP_URL и python -m bot без временного туннеля. Обязательно проксировать и страницу, и /api/ на тот же Python-сервер. Если сеть блокирует Cloudflare, нужен другой доступный HTTPS-прокси.

Подробнее: [MINIAPP.md](MINIAPP.md). Авторизация соответствует [документации Telegram](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app).

## Подтверждение платежа и возврата

Покупатель нажимает «Оплатить через ЮKassa», открывает страницу провайдера и использует только официальные тестовые данные. Сервер передаёт сумму сохранённого заказа. Статус проверяется через Payment.find_one каждые 15 секунд и кнопкой проверки. Сверяются ID платежа, metadata.order_id, сумма, валюта и состав заказа. Только succeeded вызывает общий обработчик и receipt. Повторы защищены транзакцией, одноразовым ключом заказа и ограничениями UNIQUE. canceled не создаёт поступления.

Полный возврат запускается менеджером через API ЮKassa. refund_pending не меняет финансовые суммы. Refund.find_one должен подтвердить succeeded, исходный payment_id, полную сумму и валюту; только тогда создаётся refund. Повтор завершённого возврата отклоняется. Ошибка провайдера оставляет прежние суммы. Автоматическое обнаружение возвратов, сделанных вручную в кабинете ЮKassa, не реализовано — используйте кнопку возврата Mini App.

Входящих HTTP-webhook в этом варианте нет. Поле URL уведомлений в кабинете ЮKassa для текущего кода не заполняется. MINI_APP_URL не является адресом webhook. Для обработки событий бот должен работать; после запуска фоновая сверка продолжается.

Настройка ключа: [YOOKASSA_SETUP.md](YOOKASSA_SETUP.md). [Тестовые данные ЮKassa](https://yookassa.ru/developers/payment-acceptance/testing-and-going-live/testing), [API возвратов](https://yookassa.ru/developers/payment-acceptance/after-the-payment/refunds).

## Данные, деньги и старые заказы

Один файл data/foliant.db; он исключён из Git. Миграции запускаются автоматически, перед обновлением сохраните локальную резервную копию.

- users — Telegram ID и платформа.
- products — описание, цена, текущая себестоимость в копейках и доступность.
- cart_items — уникальная пара пользователь/товар, положительное количество.
- orders — покупатель, итог, статусы выдачи и оплаты, ключ подтверждения, ID ЮKassa.
- order_items — снимки названия, цены, количества и себестоимости на момент оформления.
- checkout_tokens — ключи проверки заказа.
- payments — внутренний ID, уникальный заказ, провайдер, ID провайдера/возврата, сумма, RUB, статус, даты.
- finance_operations — receipt/refund/expense, сумма, дата подтверждения UTC, заказ, внешний ID события, автор, снимок себестоимости, комментарий и ключ расхода.
- finance_notifications / order_notifications — отметки доставки уведомлений каждому менеджеру.

В finance_operations заданы UNIQUE(order_id,type), уникальный внешний ID события и уникальный ключ расхода. Статус платежа, статус оплаты заказа и запись операции изменяются одной транзакцией BEGIN IMMEDIATE. Ошибка полностью откатывает операцию. Цена и себестоимость старого заказа не меняются при изменении каталога.

У старых order_items себестоимость остаётся NULL: историческую закупочную цену нельзя достоверно восстановить из текущей. Если в выбранном периоде есть такая финансовая операция, поток вычисляется, а учебный результат отмечается неизвестным. Старые пометки «Оплачено» автоматически не превращаются в новые поступления: у них может отсутствовать подтверждённая дата и проверка провайдера. Ограничение исторического учёта описано в [FINANCE.md](FINANCE.md).

## Формулы

Денежный поток = подтверждённые поступления − подтверждённые возвраты − операционные расходы.

Учебный результат = поступления − возвраты − себестоимость оплаченных товаров + себестоимость полностью возвращённых товаров − операционные расходы.

Период — календарные дни UTC, обе граничные даты включительно. Отбор по дате подтверждения операции, а не создания заказа. Закупочную стоимость повторно в расходы не вносят. Все суммы — целые копейки, округление только при показе рублей.

Ручная сверка: книга 640 ₽, себестоимость 320 ₽, реклама 100 ₽ → поток 540 ₽, учебный результат 220 ₽. Запрос возврата ничего не меняет. После полного подтверждённого возврата в том же периоде обе величины −100 ₽. Если продажа в сентябре, а возврат в октябре: сентябрь +640/+320 ₽, октябрь −640/−320 ₽ без расходов. Поэтому возврат старого заказа может сделать текущий период отрицательным.

/summary показывает текущий месяц UTC. Для периода: /summary 2026-10-01 2026-10-31. Команда проверяет менеджера и содержит формулы. Уведомления о новых заказах и финансовых операциях отправляются в течение примерно 15 секунд. Менеджер должен предварительно открыть бота командой /start.

## API и авторизация

Mini App посылает исходную Telegram.WebApp.initData заголовком X-Telegram-Init-Data. Каждый финансовый запрос проверяет HMAC-SHA256, auth_date (TTL 3600 секунд), ID из подписанного user и MANAGER_IDS. initDataUnsafe и ID тела запроса не используются для выдачи доступа. Просроченный кабинет нужно открыть заново.

- GET /api/summary?start=YYYY-MM-DD&end=YYYY-MM-DD — сводки и журнал за период, платежи за всё время.
- POST /api/expenses — положительная целая сумма в копейках, операционный комментарий, ключ повтора.
- POST /api/payments/{id} — проверка платежа или запрос полного возврата у провайдера.

Сумма оплаты и возврата из браузера не принимается. При обрыве сети или тайм-ауте UI сохраняет прежнюю сводку, показывает ошибку и предлагает проверить журнал перед повтором: сервер мог сохранить операцию до обрыва ответа. Прямые запросы без подписи менеджера получают 403.

## Структура проекта

bot/db.py — магазин и миграции; bot/finance.py — состояния и журнал; bot/provider.py и bot/yookassa_api.py — ЮKassa; bot/web.py — HTTP API и авторизация; bot/static/index.html — Mini App; bot/handlers/ — Telegram-действия; bot/keyboards/ — кнопки; bot/finance_worker.py — сверка и уведомления; bot/launch.py — HTTPS-запуск; bot/inspect.py — просмотр базы; tests/ — проверки.

## Ограничения

Только самовывоз, один бот, полные возвраты, без частичных возвратов. Расчёт при получении не фиксирует реальную оплату автоматически и не входит в подтверждённые поступления. Учебные чеки должны соответствовать настройкам тестового магазина; реальная фискализация не проверена. Отменённый провайдером возврат сохраняется незавершённым и требует разбора, новая попытка после такой отмены не автоматизирована. Фоновая проверка требует работающей программы. Временный HTTPS-адрес зависит от доступности Cloudflare. При аварии между Telegram-отправкой и отметкой доставки уведомление может повториться; финансовая запись — нет. Реальную демонстрацию, скриншоты и публикацию репозитория выполняют отдельно.
