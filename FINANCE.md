# Финансы «Фолиант»: магазин + Mini App в одном боте

**Обновление: имитатор отключён по просьбе владельца.** Для текущего запуска используйте [YOOKASSA_SETUP.md](YOOKASSA_SETUP.md). Учебные кнопки удалены, старые нажатия и API-действия имитатора блокируются. Старые записи сохранены. Описание имитатора ниже — история реализации и пояснение серверных тестов, а не доступный способ оплаты. `PAYMENT_MODE` теперь всегда `yookassa`.

Используем одного бота: покупатели оформляют книги, менеджер открывает `/finance` и `/summary`. Mini App — HTML/CSS/JavaScript, сервер — aiohttp в том же процессе, база — тот же файл `data/foliant.db`. Второй токен не нужен. Команда `python -m bot` запускает и Telegram polling, и HTTP-сервер. В браузере нет секретов магазина или бота.

## Установка на чистой Windows

Проверенная среда: Python 3.10+, aiogram 3.31.0, aiohttp 3.14.3, python-dotenv 1.2.4, yookassa 3.12.1. Точные версии закреплены в `requirements.txt`.

В cmd из папки проекта:

```bat
py -3 -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
copy .env.example .env
notepad .env
```

Копирование делается только при первом запуске: существующий `.env` не перезаписывайте. В PowerShell вместо `copy` можно использовать `Copy-Item`. Все остальные команды одинаковые. Активация виртуального окружения не требуется: путь к нужному Python указан явно.

Заполните локально `BOT_TOKEN` и `MANAGER_IDS` (числовой ID менеджера). Узнать свой ID можно командой `/id` после запуска бота; затем впишите число в `.env`, перезапустите бота и отправьте `/start`. Для имитатора оставьте `PAYMENT_MODE=demo`. Ключи ЮKassa ему не нужны.

```bat
.venv\Scripts\python.exe -m bot
```

Страница доступна локально на `http://127.0.0.1:8080/`. В обычном браузере можно проверить внешний вид, но финансовые данные без Telegram-авторизации закрыты. Бот должен работать одним экземпляром. Если порт занят, измените `WEB_PORT` и адрес проксирования. Остановка — Ctrl+C.

## HTTPS и открытие из Telegram

Для защиты нужен публичный HTTPS-адрес, который проксирует запросы на этот сервер, включая `/api/`. Например, сервер с HTTPS reverse proxy или уже установленный туннель Cloudflare:

```bat
cloudflared tunnel --url http://127.0.0.1:8080
```

Туннель — внешняя программа, в зависимости Python не входит. Его адрес меняется при новом запуске. В `.env` запишите полученный публичный адрес в `MINI_APP_URL=https://...`, затем перезапустите бота. В личном чате менеджера отправьте `/start`, затем `/finance` и нажмите «Открыть Mini App». Это inline-кнопка `web_app`, а не обычная ссылка в браузер. На защите покажите именно её. Приложение и API должны открываться с одного HTTPS-адреса.

Публичный адрес в этом проекте автоматически не выдан: его нужно получить на вашем сервере или через туннель. `WEB_HOST=127.0.0.1` подходит для локального reverse proxy/туннеля. В контейнере с внешним прокси обычно нужен `WEB_HOST=0.0.0.0`.

Mini App передаёт **исходную** `Telegram.WebApp.initData` в заголовке `X-Telegram-Init-Data`. В URL она не попадает. Каждый финансовый GET/POST проверяет HMAC-SHA256 по алгоритму Telegram, возраст `auth_date` (по умолчанию 3600 секунд, будущее до 30 секунд для погрешности часов), отсутствие повторяющихся полей и ID менеджера из подписанного `user`. Подмена ID в теле запроса не даёт прав. Подпись без роли менеджера даёт 403. Просроченный кабинет нужно закрыть и открыть из бота заново. Обход авторизации для localhost не предусмотрен. HTTP access log отключён, чтобы не сохранять авторизационные данные.

Официальная документация: [кнопки и проверка initData](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app).

## Путь учебного платежа

1. Покупатель выбирает книги, меняет корзину, вводит вымышленное имя, выбирает самовывоз.
2. На экране проверки нажимает «Демонстрация без платёжного провайдера». Заказ сохраняется, сервер создаёт `payments` со статусом `pending`, суммой **из заказа**, валютой RUB и внутренним ID.
3. Отдельные кнопки «Учебный успех» / «Учебная отмена» переводят платёж в `succeeded` / `canceled`. Покупатель может менять только собственный demo-платёж. Ожидающий платёж можно открыть снова через «Мои заказы» даже после перезапуска.
4. Общая серверная функция `finance.apply_event` сверяет ID платежа, ID заказа, провайдера, сумму, валюту, состав заказа и допустимый переход. При успехе статус и операция `receipt` пишутся **одной транзакцией**. Двойное/одновременное событие не удваивает деньги.
5. Менеджер получает уведомление в течение примерно 15 секунд, видит платёж и журнал в Mini App. Самовывоз «при получении» не создаёт вымышленного поступления.
6. «Вернуть полностью» создаёт `refund_pending`. Суммы пока прежние. Отдельная учебная кнопка подтверждает `refund_succeeded` и записывает `refund`. Кнопка имитации ошибки показывает ошибку и сохраняет исходные суммы. После ошибки можно повторить подтверждение.

Имитатор и ЮKassa используют одну функцию `apply_event`, одни проверки и один журнал. В имитаторе сумма и ID для события берутся сервером из платежа, не из кнопки или браузера. Для ЮKassa — из ответа её API с обязательным сравнением с сохранёнными значениями.

## ЮKassa и полный возврат

Существующая кнопка ЮKassa сохранена. Локально заполните `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY`, `YOOKASSA_RECEIPT_EMAIL`. Для отключения учебных кнопок покупателя поставьте `PAYMENT_MODE=yookassa`. В кабинете уже созданные demo-платежи остаются явно подписаны.

Создание платежа использует стабильный ключ идемпотентности заказа; проверка вызывает `Payment.find_one`. Проверяются ID провайдера, сумма, валюта и `metadata.order_id`. Только `succeeded` записывает поступление. Фоновая сверка работает каждые 15 секунд, пока бот запущен; после перезапуска проверка продолжается. Собственного публичного webhook нет. Ошибка API оставляет прежние суммы и повторяется при следующей сверке.

Полный возврат в Mini App вызывает `Refund.create` со стабильным ключом. Сначала сохраняется `refund_pending`, затем проверяется `Refund.find_one`. Только подтверждённый `succeeded`, совпавшие ID исходного платежа, сумма и валюта создают запись возврата. Ошибка/отмена провайдера не уменьшает поступления. При тайм-ауте создания повторите запрос — ключ предотвращает второй возврат. При отмене возврата провайдером интерфейс показывает ошибку, состояние остаётся незавершённым; создание нового возврата после такой отмены этим учебным проектом не автоматизировано. Частичных возвратов нет. Автоматическое обнаружение возвратов, созданных вручную в кабинете ЮKassa, не реализовано: в этом варианте используйте кнопку API-возврата в Mini App.

Настройки чека должны соответствовать настройкам тестового магазина. Учебная почта и НДС без налога — лишь демонстрационный пример. Реальная торговля и фискальные настройки здесь не проверены. Фактическая оплата/возврат у ЮKassa требуют вашего тестового магазина; локальные тесты используют подставленные ответы и не доказывают приём платежа у провайдера.

Тестовые карты берите только из [официальной документации ЮKassa](https://yookassa.ru/developers/payment-acceptance/testing-and-going-live/testing). Возвраты описаны в [документации API возвратов](https://yookassa.ru/developers/payment-acceptance/after-the-payment/refunds). Платёжные данные в чат, код и скриншоты не передавайте. Для имитатора карты вообще не нужны. `PROVIDER_TOKEN` оставлен именем переменной в `.env.example`; redirect-интеграция его не использует.

## Данные и миграция

Миграция автоматическая при старте; существующие корзины и заказы сохраняются. Перед обновлением сохраните локальную резервную копию файла базы. Для будущих заказов `order_items.cost_kopecks` копируется из `products.cost_kopecks` в транзакции оформления. Учебные себестоимости шести книг: 320, 450, 360, 280, 240, 300 рублей. Для старых позиций заказа оставляется NULL: прежняя себестоимость неизвестна, по текущей цене она не восстанавливается. Если подтверждённая финансовая операция относится к такому заказу, денежный поток вычисляется, а учебный результат за период отображается как неизвестный, не как фиктивный ноль.

`payments`: внутренний ID, уникальный заказ, провайдер demo/yookassa, уникальный ID провайдера при наличии, сумма в целых копейках, RUB, статус, ID возврата и даты.

`finance_operations`: receipt/refund/expense, положительная сумма, дата подтверждения UTC, заказ при наличии, уникальный внешний ID события, автор, комментарий, сохранённая сумма себестоимости и ключ расхода. UNIQUE(order_id,type) допускает ровно одно поступление и один полный возврат на заказ. Состояние платежа, статус оплаты заказа и запись поступления/возврата меняются одной SQLite-транзакцией `BEGIN IMMEDIATE`. Ошибка откатывает все изменения. Финансовый журнал не редактируется через UI.

Старые заказы с ранее поставленным «Оплачено» не импортируются в журнал автоматически: достоверная дата подтверждения и прежняя себестоимость отсутствуют. Это явно ограничивает отчёты операциями после внедрения журнала. Новую оплату старого ожидающего заказа система может проверить у провайдера и записать датой проверки. Для исторически точного учёта старых платежей нужна отдельная сверка выписки, здесь её нет. Уведомления и их получатели сохраняются в `finance_notifications` / `order_notifications`; после перезапуска доставка повторяется только для неподтверждённых уведомлений. При аварии между отправкой Telegram и сохранением отметки одно уведомление может повториться; деньги повторно не записываются.

## Формулы и ручная сверка

Даты в кабинете включительно, часовой пояс UTC, используется дата подтверждения операции, не дата заказа.

**Денежный поток = поступления − возвраты − операционные расходы.**

**Учебный результат = поступления − возвраты − себестоимость оплаченных товаров + себестоимость полностью возвращённых товаров − операционные расходы.**

Кнопка запроса возврата ещё не создаёт операцию. Закупка товара уже учитывается себестоимостью, поэтому её нельзя повторно внести в расходы. Ввод расходов — только для доставки, рекламы и других операционных затрат. Все расчёты — целые копейки. Только отображение преобразует их в рубли.

Пример: книга 640 ₽, себестоимость 320 ₽, реклама 100 ₽. После оплаты поток = 540 ₽, результат = 220 ₽. После полного подтверждённого возврата в том же периоде обе величины = −100 ₽. Если оплата была в сентябре, а полный возврат в октябре без расходов: сентябрь +640 ₽ потока / +320 ₽ результата, октябрь −640 ₽ потока / −320 ₽ результата. Отрицательный текущий период здесь закономерен.

`/summary` даёт текущий месяц UTC. `/summary 2026-10-01 2026-10-31` — выбранный период. Каждая сводка содержит период и формулы. Mini App показывает журнал за период и список платежей за всё время (это отдельно подписано).

API: `GET /api/summary?start=YYYY-MM-DD&end=YYYY-MM-DD` возвращает обе сводки и журнал; `POST /api/expenses` записывает расход с ключом повтора; `POST /api/payments/{id}` обрабатывает доступные действия. Все финансовые маршруты требуют подписанную Telegram-авторизацию менеджера. Внутренний обработчик событий из браузера напрямую не вызывается.

## Проверка и сдача

```bat
.venv\Scripts\python.exe -m unittest discover -s tests -v
.venv\Scripts\python.exe -m bot.inspect
```

Автотесты используют отдельные временные SQLite-файлы и вымышленные ID. Проверяются прежний путь корзины, повторное и параллельное подтверждение, жизненный цикл demo-платежа и возврата, повторы финансовых событий, неправильная сумма/валюта/заказ/ID, откат транзакции при ошибке журнала, сохранение цены и себестоимости, возврат другого периода, неизвестная старая себестоимость, подпись/срок/роль Telegram и отказ каждого финансового API постороннему.

Результат автоматической проверки при реализации: **18 тестов прошли**. Дополнительно проверены импорт обработчиков и синтаксис JavaScript (`node --check`). Визуальная проверка в настоящем Telegram WebView и реальная тестовая оплата ЮKassa не проводились: публичный HTTPS, менеджер и тестовый магазин в локальной конфигурации ещё не заданы.

Ручная демонстрация (результат заполните после фактического запуска в Telegram):

1. Пользователь А: две книги, изменить количество, удалить вторую → итог пересчитан; подтвердить demo-платёж → один receipt и уведомление менеджеру. Фактически: не проверено в этой среде.
2. Дважды нажать учебный успех → один receipt. Пользователь Б не видит корзину/заказ А, не может открыть финансовый API → отказ. Фактически: автоматика проверяет серверную изоляцию, два реальных клиента Telegram ещё не демонстрировались.
3. Менеджер открывает /finance из бота по HTTPS → данные и журнал доступны; покупателю отказ. Фактически: нужна публикация вашего HTTPS-адреса.
4. Добавить операционный расход 100 ₽ → уменьшились обе величины. Повторить запрос с тем же ключом → один расход. Фактически: проверяется автоматически.
5. Запросить возврат → сводка прежняя; имитировать ошибку → прежние суммы; подтвердить → один refund и возврат себестоимости. Фактически: проверяется автоматически.
6. Остановить и запустить программу → заказ, платёж, журнал и сводка сохранены; сравнить две даты через /summary. Фактически: повторное открытие файла проверяется автоматически; скриншот из Telegram нужно сделать вручную.

Скриншоты и запись реальной демонстрации создаются после запуска с вашими двумя учебными аккаунтами. В репозитории должны быть код, tests, README, FINANCE, requirements и `.env.example`; настоящего `.env`, файла базы и скриншотов секретов быть не должно. Ссылка на репозиторий не создана автоматически.

Новые файлы: `bot/finance.py` — транзакции и журнал; `bot/provider.py` — проверенные ответы ЮKassa; `bot/web.py` — авторизация и API; `bot/static/index.html` — Mini App; `bot/handlers/finance.py` — demo-кнопки и команды; `bot/finance_worker.py` — сверка и уведомления; `tests/test_finance.py` — проверки.
