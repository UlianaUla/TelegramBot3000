# Этап 3. Склад и распродажа последнего товара

Репозиторий для сдачи: [UlianaUla/TelegramBot3000](https://github.com/UlianaUla/TelegramBot3000).

Продолжение того же магазина, бота, Mini App и файла `data/foliant.db`. Тестовая ссылка ЮKassa сохранена. Публичные учебные кнопки не возвращены; имитатор, управляемое время и принудительные остановки существуют только в изолированном loopback-стенде `bot.stock_lab`.

## Правила

Менеджер в «Финансы · Mini App» видит склад и оформляет поступление. На складе (`on_hand`) — ещё не проданное, включая резерв. В резерве (`reserved`) — сумма активных резервов. Доступно = on_hand − reserved. Везде целые неотрицательные числа, reserved ≤ on_hand. В корзине товар не резервируется.

При подтверждении весь состав получает резерв на `RESERVATION_SECONDS`, по умолчанию **120 секунд**. Все позиции проверяются и резервируются вместе с заказом и журналом одной транзакцией. Если одной книги не хватает, нет ни заказа, ни частичного резерва. Отказ сохраняется для ключа запроса; новая попытка покупки требует нового ключа.

Успех оплаты принимается как продажа только если резерв active и серверное время **строго меньше** expires_at. На границе времени он уже истёк. Для учебного проекта время нажатия оплаты у покупателя не учитывается: учитывается момент обработки доверенного успешного события сервером. Это показано в интерфейсе.

Оплата, отмена и истечение проверяют тот же резерв внутри BEGIN IMMEDIATE. Первый допустимый зафиксированный переход побеждает. Оплаченный consumed-резерв не освобождается отменой. Отдельный статус выдачи не списывает склад второй раз; выдача неоплаченного нового заказа запрещена.

Если успешное подтверждение пришло после освобождения, оно не игнорируется: order.stock_state=payment_conflict, одно денежное поступление, нулевая себестоимость, постоянное задание возврата. Другой покупатель сохраняет свой товар. Возврат поздней оплаты не создаёт складское поступление. Возврат принятой продажи восстанавливает товар и себестоимость один раз.

Расчёт при получении оставлен для совместимости: он тоже резервирует на заданный срок, но сам по себе не подтверждает деньги и не списывает товар. Этот учебный этап демонстрирует принятую продажу через ЮKassa. Автоматического подтверждения физической наличной оплаты нет; неоплаченный наличный резерв истечёт. Для защиты используйте онлайн-тестовую оплату или изолированный стенд.

## Запуск на Windows

Версии зависимостей прежние, закреплены в `requirements.txt`: aiogram 3.31.0, aiohttp 3.14.3, python-dotenv 1.2.4, yookassa 3.12.1. Python 3.10+ и стандартный SQLite.

Перед первым запуском обновлённого кода остановите старую программу. Сохраните локальную резервную копию `data/foliant.db`. Не публикуйте её. Настройки и исходные заказы не удаляются.

```bat
cd /d "C:\Users\User\Desktop\Telegram bot"
python -m pip install -r requirements.txt
python -m bot
```

Для Mini App внутри Telegram вместо обычного запуска:

```bat
start-miniapp.cmd
```

Либо `.venv\Scripts\python.exe -m bot.launch`, если зависимости установлены в виртуальном окружении. Не запускайте второй polling-экземпляр вместе с первым. Подробная настройка HTTPS — в MINIAPP.md. Обновите `/start` и кнопку `/finance` после перезапуска туннеля.

В `.env` можно добавить `RESERVATION_SECONDS=120`; секреты и ключи оставьте локально. Миграция автоматическая. На новом складе все остатки **ноль**. Старые продажи не переносятся в резерв и не списываются задним числом.

## Явное поступление

В Mini App откройте «Склад», выберите товар, введите целое положительное количество и нажмите «Оформить поступление». Данные перечитываются с сервера после подтверждения. Для локального оператора также есть CLI:

```bat
python -m bot.stock_cli receive --product 1 --quantity 10 --key opening-stock-book-1
python -m bot.stock_cli show
```

Повтор того же ключа с теми же данными не добавляет ещё 10. Другие данные с тем же ключом отклоняются. Новое поступление — новый ключ. CLI меняет рабочую базу только по явной команде receive; в проверках используется отдельный путь.

После поступления 10 единиц первый товар показывает 10/0/10. Не заменяйте это ручным UPDATE inventory: каждая дельта должна объясняться журналом.

## Данные и совместимость

- `inventory(product_id,on_hand,reserved)` с SQLite CHECK, включая проверку целого типа.
- `reservations(order_id,state,expires_at,release_reason)`; active / consumed / released.
- `reservation_items(order_id,product_id,quantity)`; положительное целое количество, уникальная строка товара.
- `inventory_movements(kind,product_id,delta_on_hand,delta_reserved,order_id,created_at,author,operation_key)`; уникальный ключ.
- `checkout_requests(user_id,request_key,fingerprint,cart_json,result_json)`; UNIQUE(user_id,request_key).
- `refund_jobs(payment_id,state,operation_key,attempts,next_attempt_at,lease_until,last_error,reason,created_at,provider_refund_id)`; один job и один постоянный ключ на платёж.
- Дополнены прежние `orders.stock_state` и `checkout_tokens.cart_json`. Старые `orders.status` и его ограничения сохранены: это статус выдачи. Новое отдельное поле — жизненный цикл распродажи.

Состояния заказа: legacy / awaiting_payment / paid / canceled / expired / payment_conflict / refunded. Старые заказы мигрируют как legacy и не меняют склад. Состояние платежа и резерва хранится отдельно. Название, цена и себестоимость order_items остаются снимками.

Связь в одной базе: товар → reservation_items → reservations/order → order_items/payment → finance_operations. Журнал склада с order_id объясняет reserve/sale/release/return; поступления не обязаны иметь заказ.

BEGIN IMMEDIATE получает блокировку записи до чтения остатка; товары обрабатываются по возрастанию ID. Дополнительно UPDATE резерва условный, с проверкой изменённой строки. Независимые соединения/процессы конкурируют на SQLite, mutex процесса не используется. Ожидание блокировки — до 5 секунд на попытку, до трёх попыток BEGIN; исчерпание даёт понятную ошибку, а не фиктивный отказ по отсутствию товара. Сохраняйте прежний ключ при сетевом повторе.

## Восстановление и очередь возвратов

При запуске просроченные active-резервы освобождаются до polling. Далее отдельный цикл делает это каждые 5 секунд. Долгий запрос ЮKassa выполняется в другом цикле и не задерживает таймер склада. Таймер страницы только показывает оставшиеся секунды с поправкой на серверное время.

Поздний платёж, receipt и refund_job фиксируются вместе. Worker сначала арендует job короткой транзакцией на 30 секунд, затем делает внешний запрос **без открытой транзакции**. Ошибка сохраняет last_error, attempts и следующую попытку через 5–60 секунд. После аварии аренда истечёт и job продолжится. При успешном подтверждении состояние платежа, финансовый refund, складской return (только для принятой продажи) и завершение job фиксируются одной транзакцией.

Если ID возврата известен, сначала `Refund.find_one`. Если ответ создания потерян, сначала `Refund.list(payment_id=...)` с просмотром страниц. Уже созданный полный возврат сверяется по платежу, сумме и валюте. При отсутствии результата используется **тот же** постоянный ключ `foliant-refund-{payment_id}`. Близко к окончанию срока идемпотентности (23 часа для повторного создания) автоматическая новая попытка блокируется для ручной сверки, а не рискует вернуть дважды. Несколько/частичные возвраты или canceled переводят задачу в manual_review, не уменьшая поступления фиктивно. В Mini App ошибка остаётся видимой; «Повторить сверку возврата» ставит повтор проверки, но не отменяет защиту от дубликата.

Правила провайдера: [идемпотентность ЮKassa](https://yookassa.ru/developers/using-api/interaction-format#idempotence). [BEGIN IMMEDIATE](https://www.sqlite.org/lang_transaction.html).

## Деньги и себестоимость

Поток = receipt − refund − expense. Учебный результат = receipt − refund − себестоимость принятых продаж + восстановленная себестоимость принятых возвратов − expense. Поздняя оплата даёт receipt с cost_amount=0; её refund тоже имеет нулевую себестоимость. До подтверждения возврата временный денежный приток показан и объяснён в Mini App и комментарии операции.

Пример при цене 1200 ₽/себестоимости 700 ₽: А потерял резерв, Б купил последнюю единицу. Оплата А позже дала второй receipt, затем refund А. Денежный поток 2400 − 1200 = **1200 ₽**, себестоимость только Б **700 ₽**, результат **500 ₽**. Склад 0/0/0. Повторы событий ничего не меняют.

## Защищённые API

Каждый `/api/stock...` проверяет исходную Telegram initData, HMAC, возраст и разрешённый manager ID. Прямое изменение on_hand/reserved, срока или статуса оплаты из браузера не предусмотрено. Поступление принимает только product_id, quantity, key.

`/shop/cart`, `/shop/checkout`, `/shop/cancel`, `/shop/orders/{id}` используют ту же подпись Telegram, но допускают покупателя. ID берётся из подписи, не из JSON. Цены/себестоимость — из каталога и сохранённой корзины. Checkout принимает только key/items/name, сверяет items со своей серверной корзиной; поля amount/user_id/expires_at отклоняются. Чужие заказ и отмена недоступны.

Публичных `/test/*` нет. Только отдельный `bot.stock_lab`, привязанный к 127.0.0.1 и разрешённой тестовой директории, содержит управление часами/ошибками/точками остановки. Он не читает `.env` и не знает секретов настоящего бота/ЮKassa.

## Автоматическая приёмка одной командой

```bat
python -m bot.stock_acceptance
```

Команда сама создаёт свежий `data/stock-tests/run-...`, два отдельных Python HTTP-процесса с общей SQLite, вымышленные личности с подписанными данными и отдельный файл имитатора провайдера. Для каждого сценария — новая база. Корзины готовятся по HTTP; запросы покупки ждут общего стартового сигнала asyncio.Event и идут параллельно, а не последовательным циклом. Каждый HTTP-обработчик использует независимое соединение через worker thread.

Проверяются все 13 сценариев документа. Конкуренция 1/20, 10/50 и оплата/отмена повторяется не менее пяти раз. Проверяются реальные таблицы, журнал движений, финансовые суммы, состояния и ограничения. Техническая ошибка не считается отказом по нехватке. При провале команда заканчивается ненулевым кодом и записывает ошибку.

Для изменения параметров на защите:

```bat
python -m bot.stock_acceptance --ttl 30 --stock 3 --buyers 12 --repeats 5
```

Обязательные 1/20 и 10/50 сохраняются; дополнительно выполняется заданная конкуренция 3/12. Проверки нехватки используют длинный тестовый срок 3600 секунд, чтобы истечение не маскировало конкуренцию. Для границ времени используются управляемые часы стенда, без ожидания реальных 120 секунд.

Первый фактический полный прогон: 13/13 прошли. Итоговый текущий прогон и точные результаты — **STOCK_REPORT.md**. Полный JSON и SQLite остаются в указанном там `data/stock-tests/run-.../report.json`. Эти файлы исключены из Git и не содержат рабочих реквизитов.

Старые и модульные новые проверки:

```bat
python -m unittest discover -s tests -v
node tests/test_ui.cjs
```

Для ручной подготовки отдельного стенда:

```bat
python -m bot.stock_cli prepare-test --db data/stock-tests/manual/case.sqlite3 --stock 1 --buyers 20 --ttl 120
python -m bot.stock_lab --db data/stock-tests/manual/case.sqlite3 --ready data/stock-tests/manual/ready.json --ttl 120
```

В ready.json записан локальный порт. Подготовлены покупатели с вымышленными ID 1000–1019 и корзинами; внутренние подписанные запросы показаны в stock_acceptance.py. Это отдельный локальный тестовый сервер, не способ отключения авторизации настоящего Mini App. Чтобы открыть новый чистый стенд, выберите новый путь — prepare-test не перезаписывает существующий файл.

Сброс только явно выбранного старого автоматического прогона:

```bat
python -m bot.stock_acceptance --reset data/stock-tests/run-ИМЯ_ИЗ_ОТЧЕТА
```

Команда принимает только одну директорию `run-*` непосредственно внутри `data/stock-tests`, проверяет абсолютный путь перед удалением. Рабочая `data/foliant.db` и произвольные пути не принимаются. Результат сброса — удаление именно этой изолированной директории, восстановление её не предусмотрено.

## Аварийные точки и фактический дефект

Точки `checkout_after_order` / `checkout_before_commit` и `after_late_commit` вызывают `os._exit(77)` только если учебный сервер назначил fault_hook. Для первого случая проверяется настоящий rollback SQLite после гибели процесса; для позднего платежа — наличие receipt и job до рестарта. Ошибка провайдера и потерянный ответ воспроизводятся кодом отдельного SQLite-имитатора, а не ручной заменой статусов платежа в таблице. После рестарта сверяется уже созданный внешний возврат.

Первый сбой Windows и исправление обработки старых событий сохранены в **STOCK_DEBUG_LOG.md**. Исходный неуспешный запуск не назван пройденным. Пояснение для защиты: поздний денежный возврат не восстанавливает склад, потому что эта оплата не была принятой продажей; это проверяется сценарием 9 и журналом.

## Сдача и ограничения

Исходники, изменения схемы, пример переменных и проверки есть в проекте. Публикация исходников выполняется отдельно от тестового прогона. Не выполнялась автоматически запись настоящего Telegram/Mini App с двумя людьми. Для записи: поступление → резерв → оплата → остатки/финансы; затем последняя единица → просрочка А → продажа Б → поздний платёж А → возврат; отдельный рестарт с незавершённым job. Реальные деньги не нужны, используйте тестовый магазин и вымышленные имена. На записи не показывайте ключи, токены, сырую initData и настоящие реквизиты.

Один склад, целые количества, один платёж и полный возврат. Частичных возвратов/брака/нескольких складов нет. Журнал UI показывает последние 500 движений и последние 200 исторических записей вместе со всеми активными резервами/незавершёнными jobs. Длительная недоступность ЮKassa оставляет видимый ожидающий возврат и требует возобновления сети или ручной сверки. Клиентский таймер не является основанием продажи. Физическую кассовую оплату этот этап не подтверждает автоматически.
